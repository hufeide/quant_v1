## 一、严重问题（必须修复）

### 1.1 涨跌停判断不分板块（`src/broker/simulated.py`）

**问题**：`is_limit_up` 和 `is_limit_down_sealed` 对所有板块使用 ±10%，实际规则如下：

| 板块 | 涨停幅度 | 跌停幅度 |
|------|---------|---------|
| 主板（60xxxx, 00xxxx） | ±10% | ±10% |
| 创业板（30xxxx） | ±20% | ±20% |
| ST 股 | ±5% | ±5% |

**影响**：创业板股票涨停价 12.0（从 10.0），代码判断 `12.0 >= 10.0 × 1.10 × 0.999 = 10.989` → 返回 `True`（碰巧正确）。但创业板跌停价 8.0，代码判断 `8.0 <= 10.0 × 0.90 × 1.001 = 9.009` → 返回 `True`（碰巧正确）。

**实际出错场景**：创业板股票 11.5（涨 15%），代码 `11.5 >= 10.989` → `True`（涨停，拒买），但真实创业板涨停是 20%，11.5 并未涨停 → **错误拒买**。

ST 股跌停价 9.5（跌 5%），代码 `9.5 <= 9.009` → `False`（非跌停，可卖），但真实 ST 跌停是 5%，9.5 就是跌停价 → **错误放行卖出**。

**修复**：

```python
def _limit_pct(self, code: str) -> float:
    """按板块返回涨跌幅比例"""
    c = str(code)
    if "ST" in c: return 0.05
    if c.startswith("30"): return 0.20
    return 0.10

def is_limit_up(self, price: float, pre_close: float, code: str = None) -> bool:
    pct = self._limit_pct(code) if code else 0.10
    return price >= pre_close * (1 + pct) * 0.999

def is_limit_down_sealed(self, price: float, pre_close: float,
                         limit_down: float = None, code: str = None) -> bool:
    ld = limit_down if limit_down is not None else pre_close * (1 - self._limit_pct(code or ""))
    return price <= ld * 1.001
```

### 1.2 量比指标使用含当日的移动平均（`src/indicators.py`）

**问题**：

```python

**修复**：

out["vol_ma5"] = sma(out["volume"], 5).shift(1)   # 不含当日
out["vol_ratio_5"] = out["volume"] / out["vol_ma5"]
```

## 二、未来函数（Lookahead）风险

### 2.1 MA 支撑检查用末日 MA20 套全回调期（`src/indicators.py`）

**问题**：

```python
ma_ok = not np.isnan(ma_vals[i]) and min(df["low"].values[j + 1:i + 1]) >= ma_vals[i]
```

把回调期最低点 `min(low)` 与**末日**（第 i 日）的 MA20 比较，而不是与回调期**每日各自的** MA20 比较。这两个判定不等价：回调期 MA20 是变动的，用末日值套整个区间，方向上并不保证保守。

**正确做法**：逐日比较，每天的 low 与当天的 MA20 比较：

```python
lows = df["low"].values[j + 1:i + 1]
mas = df[ma_col].values[j + 1:i + 1]
ma_ok = not np.any(np.isnan(mas)) and all(lows[k] >= mas[k] for k in range(len(lows)))
```

**实测影响（300 组随机构造数据，随机搜索符号与幅度）**：

| 结果 | 次数 | 占比 |
|------|------|------|
| 两判定一致 | 273 | 91% |
| **假阴性**（真实满足 MA 支撑，代码判 False → **漏信号**） | 27 | **9%** |
| 假阳性（真实已跌破，代码判 True → 误触发） | 0 | 0% |

**结论**：该 bug 的实际效果是**方向性地漏掉信号**（9%），而非引入未来的上涨信息。这不会污染回测收益（不会买入不该买的），但会系统性减少缩量回踩策略的成交次数，使该策略的收益被低估。

在构造数据中未找到假阳性方向：末日反弹抬升 MA20 的同时，最低 low 也同步下移，两者通常同步恶化。

### 2.2 `detect_uptrend_and_pullback` 放在 indicators.py 而非检测器内

**问题**：该函数定义在 `src/indicators.py` 中，是形态识别逻辑，与"技术指标"的语义不符。且它依赖 `df` 的列结构（需含 `ma{N}` 列），与指标计算的无状态特性不一致。

**建议**：移入 `src/detectors/pullback.py` 作为 `PullbackDetector` 的私有方法，或拆分为独立的 `src/patterns.py` 模块。

## 四、配置不一致

### 4.1 `config.yaml` 中 overheat_exclude 开关矛盾

```yaml
universe:
  overheat_exclude_enabled: false    # 顶层开关：false
  filters:
    overheat_exclude: true           # 消融开关：true
```

`filter_universe` 中的判断逻辑：

```python
if _on("overheat_exclude") and get_config("universe.overheat_exclude_enabled", False):
```

两个开关都需为 `true` 才生效。当前配置 `overheat_exclude_enabled: false` → 过热排除实际上不生效，但消融实验中的 `universe_no_overheat` 实验试图关闭它时，由于它已经是关闭状态，实验结果将与基线完全一致，无法测量该过滤的贡献。

**修复**：将 `overheat_exclude_enabled` 设为 `true`（如果确实要启用），或在消融实验中同时操作两个开关。

### 4.2 `config.yaml` 缺少 `ablation` 段

`src/ablation/config.py` 定义了 `ABLATION_DEFAULTS`，但 `config.yaml` 中没有 `ablation:` 段。`merge_ablation` 函数需要从 `base.get("ablation", {})` 读取，如果 base 没有该段则使用空字典合并。

**建议**：在 `config.yaml` 中添加 `ablation:` 段并填入 `ABLATION_DEFAULTS` 的内容，保证配置文件自洽。

## 十、回测引擎层（`strategies/arena_base.py`）

### 10.1 `pf.buy_count_today` 从不重置（严重）

**问题**：`Portfolio.reset_daily_counters()` 定义了但 `arena_base.py` 从未调用。`next()` 末尾重置的是策略自己的 `self.buy_count_today`，而真正参与 `can_open()` 判断的是 `pf.buy_count_today`。

```python
def next(self):
    ...
    # 重置当日计数（实际应在次日，简化处理）
    self.buy_count_today = 0        # ← 重置的是策略的计数器，不是 pf 的
```

**实测**：

| 交易日 | can_open | pf.buy_count_today |
|--------|----------|-------------------|
| day1 | True | 1 |
| day2 | True | 2 |
| day3 | True | 3 |
| day4 | **False**（当日买入已达上限 3 只） | 4 |
| day5 | **False**（当日买入已达上限 3 只） | 5 |

**影响**：`max_buy_per_day: 3` 从"每日最多 3 只"退化为"整个回测最多 3 只"。四账户各自只买 3 只就永久停买，直接导致回测结果失真——这会让策略看起来像"几乎不交易"，与 V1 模拟盘的实际交易频率完全不符。

**修复**：在 `next()` 中检测日期变化时调用 `pf.reset_daily_counters()`，而非在末尾无条件重置策略计数器：

```python
def next(self):
    new_date = self.datas[0].datetime.date(0).isoformat()
    if self.current_date != new_date:
        for pf in self._all_portfolios():
            pf.reset_daily_counters()
    self.current_date = new_date
    ...
```

### 10.3 `limit_down` 硬编码 `pre_close × 0.90` —— 创业板止损无法执行（严重）

**问题**：`_execute_sells` 中

```python
limit_down = pre_close * 0.90      # 对所有板块一律 -10%
...
sealed=False,   # 简化：不判断封死
```

创业板跌停幅度是 20%，真实跌停价 = `pre_close × 0.80`，比代码认定的低 10 个百分点。由于 `is_limit_down_sealed` 判据是 `price <= limit_down × 1.001`，代码把一切 `price <= 0.901 × pre_close` 的价位都判为"跌停封死"。

**实测（昨收 20.00，代码 limit_down = 18.00，真实跌停价 = 16.00，封死判定上限 18.018）**：

| 现价 | 昨收下方跌幅 | 真实状态 | 代码判定 | sell 结果 |
|------|------------|---------|---------|-----------|
| 18.50 | 7.5% | 正常 | 未跌停 | 成交 ✓ |
| 18.02 | 9.9% | 正常 | 未跌停 | 成交 ✓ |
| 17.00 | 15.0% | **正常可卖**（距真实跌停价 16.00 还有 6.25%） | 跌停封死 | **不成交** ← |
| 16.00 | 20.0% | 跌停价，能否卖出取决于封单 | 跌停封死 | 不成交 |
| 14.00 | 30.0% | 不可能出现（股价无法跌破跌停价） | 跌停封死 | 不成交 |
| 10.00 | 50.0% | 不可能出现（股价无法跌破跌停价） | 跌停封死 | 不成交 |


**注意**：真实交易中股价不会跌破跌停价（16.00），因此 14.00 和 10.00 两行代表不可能发生的价格。代码把它们也判为跌停封死，本身无害。但 **17.00 这一行才是关键——价格距跌停价还有 6.25% 的空间，完全可以卖出，代码却禁止了**。

**关键：被误判封锁的区间是 `(−∞, −9.91%]`，不是有限区间**。`1.001` 这个容差只往上扩了 0.1%，向下则无限延伸——任何跌幅超过 9.91% 的价位都卖不掉。

**影响**：R1 止损（浮亏 −6%）能否执行取决于成本价。止损触发价 = `cost × 0.94`，能卖出的条件是 `cost × 0.94 > 0.901 × pre_close`，即 `cost > 0.9585 × pre_close`。

| 持仓成本 | 昨收 | 止损触发价 | 能否卖出 |
|---------|------|----------|---------|
| 20.00 | 20.00 | 18.80 | 能（跌 6% 时未超 9.91% 阈值） |
| 19.50 | 20.00 | 18.33 | **不能** |
| 19.15 | 20.00 | 18.00 | **不能**（恰好触界） |
| 15.00 | 20.00 | 14.10 | **不能**，且跌到 −33% 仍卖不掉 |

实测成本 15.00 的创业板持仓，现价跌到 14.10（−6%，R1 触发），`broker.sell()` 返回 None；此后价格继续下跌，每轮都返回 None —— **整个持仓被永久锁死**，直到回测结束都无法卖出。这解释了为什么 `sell_reasons` 中 B3 统计为空，而亏损被无限放大。

**两处修复**：

```python
# 1. limit_down 按板块计算
ld = self.broker_sim._limit_pct(code) if hasattr(self.broker_sim, "_limit_pct") else 0.10
limit_down = pre_close * (1 - ld)
```

**2. `sealed` 恒为 False 使 B3 规则完全失效**

`b3_limit_down` 的判断是 `if sealed and price <= limit_down * 1.001`。`sealed=False` 恒传入，因此 B3 在回测中**永远不会触发**，`sell_reasons` 统计里不可能出现 B3，AB 消融实验中 B3 开关的开与关结果完全相同（见 10.6）。

需要明确"封死"的判定来源：日线数据无封单量信息，只能以"收盘价 = 跌停价"近似。

### 10.4 `sentiment_gate` 权重与 `config.yaml` 量纲不一致

`combine()` 直接加权三个子指标。`config.yaml` 中散户情绪代理是成交额突变率（比率，常在 0.5~2.0），赚钱效应是涨跌幅（百分比，常在 -3~+3），市场温度是 0~100 分。三者量纲不同，`0.45×涨跌幅 + 0.35×温度 + 0.20×比率` 的结果无物理意义，`gate_open: 52` / `gate_limit: 40` 这两个阈值也只是经验值。

**影响**：AB-03/AB-04 消融实验测量的是"某一组未归一化的加权值是否有效"，而非"情绪闸门是否有效"。即使实验通过，也无法推广到实盘——实盘需要的是各自归一化到 [0,100] 后再加权。

### 10.5 `pre_close = close[-1]` 语义正确（已验证）

`_execute_sells` 与 `_execute_buys` 中 `pre_close = data.close[-1] if len(data) > 1 else price`。实测 backtrader：

| bar | close[0] | close[-1] | 期望 |
|-----|---------|-----------|------|
| 0 | 101 | 105 | —（被 len>1 保护） |
| 1 | 102 | 101 | 101 ✓ |
| 2 | 103 | 102 | 102 ✓ |
| 4 | 105 | 104 | 104 ✓ |

bar0 的 `close[-1]` 会取到下一根 K 线的值（105），属于前视，但 `len(data) > 1` 守卫拦住了。**此写法正确，无需修改**，但守卫不能移除。


### 10.6 B3 跌停顺延的消融开关实际不可测量

`RiskManager._rule_on("B3")` 从 `ablation.risk.B3_limit_down` 读取开关，但 `config.yaml` 的 `risk` 段下没有任何 `B3_limit_down` 键（risk 段只有 12 个键，全是风控阈值，不含消融开关）。`config.yaml` 也没有 `ablation` 段。

结果是：`get_config("ablation.risk.B3_limit_down", True)` 读不到 → 始终回退默认值 `True`。要让消融实验真正区分 B3 开/关，必须用 `set_override()` 注入：

```python
set_override({"ablation": {"risk": {"B3_limit_down": False}}})
# 跑完
clear_override()
```

**实测验证**（注入 B3=False 与默认 True 对比）：

```
注入 B3=False  → check_all 返回 {'rule': 'R1', 'reason': '止损触发 浮亏-10.00%', 'priority': 3}
B3 默认(True)  → check_all 返回 {'rule': 'R1', 'reason': '止损触发 浮亏-10.00%', 'priority': 3}
→ 结果相同: True
```

即使通过 `set_override` 注入，结果仍然相同——因为 `sealed=False` 恒传入使 B3 永不触发。**B3 开关的消融实验（AB-02 中与 B3 相关的部分）无法测出任何差异**。

**修复优先级**：B3 的 `sealed` 参数必须在 `_execute_sells` 中基于真实封板信息计算（日线可近似为 `close == limit_down`），否则 B3 规则在回测中完全失效。
